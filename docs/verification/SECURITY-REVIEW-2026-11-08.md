# Security review of pihole-hardened — 2026-11-08

Scope: everything this repository ships — the image built from `Dockerfile`,
the GitHub workflows, the scripts, the deployment files and the lab. Upstream
Pi-hole code was read only where this image's behaviour depends on it
(`start.sh`, `bash_functions.sh`, `updatecheck.sh`, `gravity.sh`, the `pihole`
CLI and FTL's web server request handler). Each finding below was reproduced
on the image before the fix and re-tested after it (`scripts/smoke-test.sh`
now checks every runtime item). Severity is for this project's deployment:
a DNS sinkhole on a home or small-office LAN, not authorized for CUI.

## Findings and remediation

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | Medium | **Repository metadata served before login.** FTL's `request_handler()` only forces the login for URIs without a dot in the last path segment. Everything else is served statically. The web root is a git checkout, so `/admin/.gitignore`, `/admin/.devcontainer/devcontainer.json`, `/admin/.github/*.yml`, `/admin/README.md` and `/admin/package-lock.json` (349 KB) answered 200 to anonymous clients on this image and on `pihole/pihole:2026.10.1`. On the official image the git pack `/admin/.git/objects/pack/pack-<hash>.pack` (2.2 MB) is served too, and its name is predictable from the release tag, so the exact web version can be fingerprinted pre-login. | Image: the fetch stage deletes those files (`Dockerfile`). Deployment: `FTLCONF_webserver_advancedOpts=hide_files_patterns=**/.*` makes CivetWeb answer 404 for any dot-file (`deploy/docker-compose.yml`). Upstream: PR files for FTL (default `hide_files_patterns`) and docker-pi-hole (delete the files) in the deliverables. |
| 2 | Medium | **Mutable upstream references, no detection.** Core, Web and docker-pi-hole are fetched by git tag; FTL by release asset, checked only against the `.sha1` published next to it. Tags and assets can be replaced without the name changing, and the weekly rebuild would ship the new content with no pull request. | Every release now records what each tag resolved to (`image-digests.json`: commits, per-platform FTL SHA-256; `build-inputs-*.txt`). `scripts/check-upstream-drift.sh` runs before publishing and fails the release if a name-unchanged reference changed content, or if the three platform builds disagree. A version bump (new tag name, through a reviewed PR) sets the new baseline. The gate fails closed when the previous release can't be fetched. |
| 3 | Medium | **Trivy installer trusted the release's own checksum file.** It proves transport integrity only; a replaced release (as in the March 2026 incident) would pass. | `upstream.env` pins the SHA-256 of both Trivy tarballs; `scripts/install-trivy.sh` checks against the pin. Renovate bumps the version but not the hashes, so CI fails until a person verifies them. Both pins were cross-checked against the binaries inside `ghcr.io/aquasecurity/trivy:0.69.3` (byte-identical, amd64 and arm64). |
| 4 | Medium | **Signed downgrade accepted by the updater.** `verify-release.sh` verifies signatures but has no notion of order; `update.sh` moved to whatever "latest" pointed at. A re-published old release carries valid signatures. | `verify-release.sh` prints the release version and checks that a requested version matches the signed manifest. `update.sh` records `PIHOLE_VERSION` in `.env` and refuses to move to an older version unless `ALLOW_DOWNGRADE=1`. Tested: older refused, older with override, newer, same. |
| 5 | Low | **`source upstream.env` in workflows and scripts.** Renovate writes upstream release names into that file; a release named with shell metacharacters would execute in CI (`pull_request` has no secrets; `main` has `packages: write`). | `scripts/upstream-env.sh` validates the file (`KEY=value`, values `[A-Za-z0-9._-]`) and emits exports; all workflows and scripts source that. The lint job runs the validator first. Tested with `X=1; rm -rf /` → rejected. |
| 6 | Low | **Admin password in the container environment.** `secrets.env` put `FTLCONF_webserver_api_password` into the compose environment, visible in `docker inspect`. | Compose mounts the password as a Docker secret (`./webpassword` → `/run/secrets/webpassword`) and sets `WEBPASSWORD_FILE`, which upstream `start.sh` supports. Smoke test asserts the password is absent from the container's environment. |
| 7 | Low | **NTP server listening on 123/udp by default.** FTL's built-in NTP server was on; the NTP client could never work without `CAP_SYS_TIME`, which the container doesn't have. One more unauthenticated listener, and a repeated startup warning. | `FTLCONF_ntp_*_active=false` in compose, documented how to turn it back on. Smoke test asserts nothing listens on 123/udp. |
| 8 | Low | **Versions shown as N/A.** Removing `git` and the `.git` directories made `updatecheck.sh` write `null` for Core and Web, so `pihole -v`, the web UI footer and `/api/info/version` lost the version evidence the compliance bundle relies on. | `scripts/git-shim.sh` is installed as `/usr/bin/git`. It answers the three local queries `updatecheck.sh` makes from `build-inputs.txt` and fails loudly for anything else. Smoke test asserts the versions file has no `null`. |
| 9 | Low | **systemd updater ran as unconfined root.** | `pihole-update.service` gains `ProtectSystem=strict`, `ReadWritePaths=/opt/pihole`, `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`, an empty capability bounding set and the usual `Protect*`/`Restrict*` set; cosign's cache is moved to a `StateDirectory`. Not testable in this sandbox (no systemd): run `systemd-analyze security pihole-update.service` and one manual `systemctl start` on the Pi. |
| 10 | Low | **Trivy noise inside the image.** `/etc/.pihole/test/*.Dockerfile` (19 files) and `/var/www/html/admin/.devcontainer/Dockerfile` produced misconfiguration findings in image scans; `package.json`/`package-lock.json` added a node-pkg target for the web repo's dev dependencies. | Removed with finding 1. Image scan: 1 target, 0 vulnerabilities, 0 misconfigurations, 0 secrets. |
| 11 | Info | **Provenance gap for the startup scripts.** The docker-pi-hole commit the scripts came from was not recorded. | `PIHOLE_DOCKER_COMMIT` build argument, written to `build-inputs.txt`, carried into the SBOMs and the drift gate. |
| 12 | Info | **macvendor.db fetched without any check.** Upstream publishes no checksum; the file is parsed by FTL (SQLite). | Header check (`SQLite format 3`) in the fetch stage; hash recorded. Residual: the database is mutable by design. |
| 13 | Info | Documentation drift: `.trivyignore` said 8 capabilities (it is 7); `cosign` version requirement was unclear (the release workflow signs with cosign 3's bundle format). | Fixed; docs now require cosign 3.x. |

## Checked and found acceptable

- **Stripping setuid from `sudo` and `su`.** Every `sudo`/`su` call in the shipped scripts is guarded by a root check (`gravity.sh`, `piholeLogFlush.sh`, `updatecheck.sh`), and the `pihole` CLI exempts the `pihole` user from its root requirement, so gravity runs from the web UI still work. Verified: `sudo -u pihole id` and `su -s /bin/sh pihole` succeed as root with no setuid bit.
- **FTL's effective capabilities are zero.** `start.sh` sets `cap_chown=ep` on the binary, but `no-new-privileges` stops file capabilities from being gained, and FTL needs none for DNS on a bridge network (Docker sets `ip_unprivileged_port_start=0`). The remaining 7 container capabilities are used by root in `start.sh` only. Smoke test now asserts `CapEff` is 0.
- **Workflows.** `permissions: {}` at the top of every workflow, per-job grants commented; all actions SHA-pinned; `persist-credentials: false`; no `pull_request_target`; no expression interpolation into `run:` blocks; artifacts are immutable within a run; the publish job verifies every tag resolves to the signed digest; keyless identities are pinned to `build.yml`/`release.yml` on `refs/heads/main`. Harden-Runner stays in `audit` mode until the first runs produce the endpoint list (`docs/SETUP.md`).
- **Renovate automerge window.** A compromised upstream release could be rebuilt into this image after the 1-day cooldown plus CI. That is inherent in a hands-free pipeline; finding 2 limits it to new tag names, which always arrive through a PR that can be reviewed.
- **Unfixed HIGH/CRITICAL findings pass the gate** (`--ignore-unfixed`). They are reported in the bundle and in code scanning; this is documented.

## Verification after the changes

- `scripts/smoke-test.sh pihole-hardened:ci`: PASS (12 checks, 36 s), including the new ones: FTL has no effective capabilities; password absent from the environment; `/admin/.gitignore`, `/admin/.github/dependabot.yml`, `/admin/README.md`, `/admin/package-lock.json` → 404 while `/admin/login` → 200; no 123/udp listener; versions reported (v6.5, v6.6.1, v6.8).
- `trivy image --scanners vuln,secret,misconfig`: 1 target, 0/0/0. Image 112 MB (unchanged).
- actionlint, zizmor (pedantic, offline), hadolint (both Dockerfiles), shellcheck (`-S warning`, all scripts), `trivy config`: clean.
- `scripts/check-upstream-drift.sh`: same content → PASS; version bump → PASS; moved tag (web commit, FTL hash) → fails with a per-reference error; platform disagreement → fails; `gh` unavailable → fails closed.
- `deploy/update.sh` with a stubbed `docker`: downgrade refused; downgrade with `ALLOW_DOWNGRADE=1`, upgrade and no-op all behave; `.env` carries `PIHOLE_VERSION`.
- Bundle build with the new `image-digests.json` fields and `build-inputs-*.txt`; SBOM helper adds 5 components including the docker-pi-hole commit.
- `scripts/upstream-env.sh`: accepts the shipped file, rejects a line with shell metacharacters.

Not verified here: the systemd unit (no systemd in the sandbox), the workflows on GitHub (first release run), the FTL patch compiled (the pattern itself was verified live through `webserver.advancedOpts` on FTL v6.8).
